# LFClaw 维护约定

维护 LFClaw 前阅读[产品与实施基线](06-架构设计/产品与实施基线.md)、[原始需求](03-需求文档/LFClaw_需求_提取.txt)和最新[工作记录](07-工作日志/README.md)。继续遵守仓库根 AGENTS.md；修改 packages 下源码前阅读 DSH 架构。

- 沟通、新增项目文档与工作记录使用中文。协议和代码标识保留必要的技术命名。
- 两端分别为企业管理 Web 与员工桌面端；DSH 是底层执行基础。需求冲突以用户最新明确要求和原始需求为准，不将旧计划中的审批、配额等自动加回。
- 客户端正式运行、本地运行、人工联调与验收统一连接正式企业服务 `http://8.216.38.213:39811/lfclaw/api`，管理页同源根路径；不自动启动本地企业服务或回退到旧地址。更换地址须有用户明确要求。自动化单元测试保留隔离数据与模拟传输，禁止将其增删改夹具指向正式数据。
- UI 设计按用户要求使用 image-2；使用前核实工具是否支持指定模型，不能冒称已使用。保留必要配置和失败状态，真实页面检查不能由效果图替代。
- 每个实质阶段及时追加中文工作记录，写清修改、验证结果、遗留事项与下一步。不能把历史报告或静态阅读写成本次运行通过，不能记录密钥或访问令牌。
- Windows 客户端交付必须对本次打包产物运行 `apps/web/tests/smoke-desktop-boot.mjs`，启动失败不得复制交付包或报告可用；修改品牌覆盖时运行 `packages/client/ui-lfclaw/tests/brand.client.spec.tsx`，不得以编译或 Host 检查代替界面验收。根目录一键入口已执行启动门禁；其他入口须补跑，见[故障复盘](07-工作日志/2026-10-21-Windows打包与白屏故障复盘.md)。
- 默认功能必须进入可重建的依赖、Profile 组合及补丁策略，不能只安装在维护者的开发 Profile。界面交付检查须确认 LFClaw 图标、文字品牌、“渠道接入”入口及设置版本与实际安装版本一致；插件默认装载不等于用户账号绑定或消息收发已验收。
- 用户已授权使用本机 SSH 别名 `sales-agent-server` 维护日本服务器上的 LFClaw。发布前核实目标身份与现行版本，只操作 `/opt/lfclaw-enterprise` 中的 LFClaw 发布文件和 `lfclaw-enterprise-admin.service`；保留业务数据、配置及回退版本，不修改或重启 `/opt/LfClaw`、`lfclaw.service` 或其他服务。遵循[发布流程](../docs/cookbook/lfclaw-release-deployment.zh.md)。
- LFClaw 正式服务端更新和客户端包交付由维护代理主动完成适用的构建、验证、上传、部署与线上检查，不把传包步骤留给用户。发布条件不足或验证失败时停止后续发布并报告当前状态；手动安装包不得冒充自动更新包。
- macOS 客户端包等待用户提供 GitHub Release 产物后再获取、核对版本与完整性，并按实际支持的发布方式上传和验证；用户提供 Release 产物不等于授权更换项目 Git 远端。未取得产物时不代为选择或发布 Mac 包。
- 每次客户端发布验证通过后，主动更新飞书项目文档的“最新安装包”附件、下载链接、平台版本和日期，回读核验并记录维护日志；未发布的平台保留历史标注，不冒称同步升级。目标与步骤见[知识库安装包同步](08-构建运行/desktop-release/README.md#知识库安装包同步)。
- LFClaw Windows 更新仅使用独立更新源与内置公钥验证的签名清单，不恢复 DeepSeek Harness 更新源。没有更新配置的历史客户端须手动安装一次；不得宣称服务器上传能给旧二进制新增能力。发布流程与私钥保管见[客户端更新发布](08-构建运行/desktop-release/README.md)。
- 项目稳定并收到用户的新 Git 地址后再整理上传；不要提前更换远端。保留开始工作时已有的改动。

- 客户端发布成功后，Windows 与 macOS 分别只保留最新两个版本，清理更早的安装包、blockmap 和对应归档，不另存服务器历史备份；遵循[客户端发布器](08-构建运行/desktop-release/README.zh.md)的校验与清理规则。
