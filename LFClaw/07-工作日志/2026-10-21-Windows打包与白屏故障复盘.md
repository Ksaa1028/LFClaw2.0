# Windows 打包与白屏故障复盘

## 结论

2026 年 10 月 21 日交付的 Windows 包 `2026102104` 能完成构建和 Host 运行检查，但真实客户端启动白屏，提示 `@deepseek-ai/dsh-client-ui-lfclaw: failed`。根因是包内 LFClaw 品牌图标与默认品牌图标以相同优先级注册单实例插槽。交付检查没有启动图形界面，维护代理将 Host 检查通过误判为客户端可用，这是本次交付遗漏。修复后的 `2026102105` 已完成真实 Electron 启动检查并显示企业激活页面；一键入口增加界面检查，失败时禁止复制交付包和报告成功。

## 遇到的错误与解决方式

| 问题与表现 | 原因 | 处理与后续约束 |
|---|---|---|
| 用户没有 `.env.windows` 或签名证书，原入口要求签名发布配置 | 本地手动安装与正式签名自动更新共用要求 | 本地入口明确生成未签名包，不读取签名配置、不启用自动更新；正式签名发布保留原校验，不把未签名包上传为自动更新包。 |
| Host、Client 聚合编译失败 | 企业连接器漏项目引用；Host 测试被 Client 编译；服务端缺独立声明构建；测试夹具遗漏字段、声明或使用不兼容 API | 补项目引用与服务端声明配置，按真实运行面归属测试，修复夹具；保留严格编译，不通过跳过类型检查交付。 |
| 打包版本不一致或找不到 LFClaw 私有插件 | 私有包版本仍是 `0.1.0`，桌面依赖要求同仓版本；npm 发布集合排除了私有包 | LFClaw 包版本对齐仓库版本，桌面单独打包私有插件；它们不进入 npm 发布。 |
| 私有插件文件清单不能覆盖分块产物 | 仅列入口文件，未完整包含构建生成的 JavaScript 分块和 CSS | 清单包含 `lib/**/*.js`、`lib/**/*.css`、`lib/**/*.d.ts`；验证对象必须是归档中实际安装的代码，不能只检查源码。 |
| Electron 下载出现 `ECONNRESET` | GitHub 下载链路失败 | 默认入口使用 Electron 镜像，依据锁定 Electron npm 包内的校验和验证内容；保留用户显式镜像配置，不关闭完整性校验。 |
| 安装器原生辅助组件编译报缺少 `windows.h` | 本机有 C++ 编译器但未安装 Windows SDK | 本机安装 Windows SDK `10.0.26100.7463` 后重建通过；新机器仍须具备 SDK，脚本不承诺自动安装所有系统工具。 |
| 打包后运行检查仍寻找 `DeepSeek Harness.exe` | 产品已命名为 LFClaw，检查中的 Windows 文件名未同步 | Windows 检查改用 `LFClaw.exe`；产品重命名必须同步安装器、可执行文件定位和验证入口。 |
| 安装后白屏，LFClaw Client 插件未激活 | `sidebar.brand.mark` 与 `conversation.hero.brand.mark` 的 LFClaw 注册与默认注册同为优先级 `0`，单实例插槽拒绝冲突 | LFClaw 覆盖注册使用 `priority: -1`。品牌回归测试覆盖两种加载顺序及卸载后恢复默认图标；重建归档确认包含修复。 |
| 旧包已失败，仍曾报告“运行检查通过” | 原检查验证原生依赖、Host、插件操作和 Office 转换，没有加载真实 Client 插件树 | 将 Host 检查与图形界面启动分别验收；根脚本必须等待真实界面检查成功后才交付。 |
| 排查期间再次出现报错窗口，用户以为新版仍失败 | 用旧包做故障复现时测试窗口显示到用户桌面 | 界面检查隔离测试数据并隐藏窗口、自动处理测试弹窗、结束时退出进程；复现旧包时明确说明版本和目的，不让用户代为点击重试。 |

## 白屏定位证据

首次用户崩溃报告为 `crash-2026-10-21T09-10-57-977Z-web-boot.log`，报告版本为 `0.2.1-alpha.2.20261021.4`。原报告只有插件失败摘要；隔离复现捕获到底层异常：`single slot "sidebar.brand.mark" already has a registration at priority 0`。检查旧包的运行目录确认品牌注册没有 `priority`，而当时工作区源码已有 `priority: -1`；源码修复不会自动更新已安装包。

重建 `2026102105` 后检查私有插件归档，确认两个品牌插槽均携带优先级修复，再启动封装后的 `win-unpacked/LFClaw.exe`。真实页面显示企业激活界面，启动检查退出码为 `0`。旧包移至本地验证归档并标为 `startup-failed`，交付目录只保留新包。

## 防复发措施与责任

| 必须满足的要求 | 已执行的保护措施 | 维护责任 |
|---|---|---|
| 品牌覆盖不能使插件初始化失败 | [品牌回归测试](../../packages/client/ui-lfclaw/tests/brand.client.spec.tsx)验证默认插件先加载、后加载以及 LFClaw 卸载恢复，三个案例通过 | 修改品牌注册、单实例插槽或插件加载方式时运行该测试。 |
| 客户端可启动必须以实际打包产物为证据 | [真实启动检查](../../apps/web/tests/smoke-desktop-boot.mjs)启动封装后的 Electron，等待 LFClaw 侧栏挂载；旧包检查失败、新包检查通过 | 不使用源码开发服务、Host 检查或安装包存在代替图形界面验收。 |
| 检查失败不得交付 | [一键入口](../../一键打包LFClaw-Windows.ps1)检查退出码，失败即停止；只有通过后才复制 `.exe` 并打印 `SUCCESS` | 不移除、跳过或将启动检查改为仅打印警告；绕过根入口打包时也必须补跑同一检查。 |
| 当前修复必须进入交付版本 | 每次分配新编号并保留占用记录，不覆盖失败版本；检查实际包内代码并报告准确文件名 | 源码或依赖变更后重建、重验，不能拿旧检查结果证明新包。 |
| 验收范围必须如实报告 | 启动检查与企业账号业务验收分别记录 | 未输入激活码、未验证安装升级及业务流程时，不写“所有功能通过”或“安装升级已验收”。 |

以上措施防止本次品牌冲突在一键交付流程中漏检，不是对任意未来缺陷的绝对保证。Windows SDK 缺失、网络不可用仍可能导致新机器打包失败；必须停止交付并报告原因，不能绕过检查继续。

## 本次记录校验

设置显示基础版本而非安装版本的原因是 Web 构建变量与桌面发布编号来自不同来源。桌面设置现改为通过受来源校验的 IPC 读取 `app.getVersion()`，保留发布后缀；读取失败显示重试提示。回归案例使用不同基础版本和桌面版本，实际产物检查打开设置并与 Electron 版本逐字比较，防止后续只修改安装器版本而漏改显示。详见[补齐记录](2026-10-21-安装包渠道与品牌补齐.md)。

后续用户验收发现 `2026102105` 缺少“渠道接入”，左上角仍有默认文字品牌。原因分别是 IM 插件只装在开发 Profile、没有进入默认包依赖，以及品牌修复只覆盖图标，漏掉独立的 `sidebar.brand.name` 插槽。新增固定版本依赖、默认桌面插件行及共享补丁策略；名称通过 LFClaw 字典和优先级覆盖注册。启动门禁扩展为同时检查图标、名称和渠道入口，运行时检查增加插件版本、群聊拒绝、已授权私聊允许和未授权私聊拒绝。该遗漏说明“能启动”不等于“默认功能交付完整”，后续不得将两者混称为验收完成。

新增复盘及维护约定中的本地链接、结尾换行和限定文件的 `git diff --check` 通过。另执行 `pnpm run test:docs`、`pnpm run doc-sync`、`pnpm run lint`，三项均未全量通过：文档检查报告仓库双语配对、生成目录、类型摘录、链接及 README 规则问题，lint 报告源码和测试中的类型规则问题。中文工作日志目录 README 也在双语配对报告内；按 LFClaw 的中文记录要求保留，未关闭配对规则或宣称全仓通过。详细输出保存在本机 `.desktop-build/incident-doc-quick.log`、`incident-doc-sync.log`、`incident-lint.log`。这三项检查属于本次文档整理，不能与上一节真实客户端启动通过的结果混为一项。
