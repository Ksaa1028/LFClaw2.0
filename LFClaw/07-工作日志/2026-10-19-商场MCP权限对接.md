# 2026-10-19 商场 MCP 楼层权限对接

> 后续修正：本文记录早先阶段。签名密钥前提及未知工具一律禁止的结论已由[商场权限网关执行修正](2026-10-19-商场权限网关执行修正.md)取代；当前方案无需修改 MCP 代码或配置，完整五项权限允许已分配且已启用的淘气堡及未知工具。

## 目标与范围

核对 `E:/code/lf-mcp-server2` 现有实现，在 LFClaw 侧保证员工不能查询未授权楼层，改权后清除旧运行权限并阻止在途旧结果返回。MCP 仓库只读，结束时 `git status --short` 为空；本次未发布版本、重启线上服务或变更真实员工权限。

## 上游核对结果

- `LfClawPermissionFilter` 仅对带非空签名的 `/mcp2/message` 验签；无签名请求继续旧路径。`ScopeService` 的旧身份路径存在空身份或鉴权失败放行全部楼层的分支，因此共享密钥本身不能阻止绕过企业网关直连。
- 签名协议为 HMAC-SHA256；字段 `sub`、`mcp`、`permissions`、`exp`。企业身份为 `openId=__lfclaw_enterprise__`、`appId=lfclaw`，签名同时作为 `appSecret`。自营对应楼层 565，企业身份不设置全局 root 标记。
- 楼层、区域、店铺三个工具的数据返回受楼层范围约束。业态、事件、结算、导购及日报相关六个工具含未过滤或跨楼层汇总，LFClaw 仅对完整五项权限开放。淘气堡工具未确认归属，未知工具也默认拒绝。完整清单见[服务端说明](../02-管理端/server/README.md#商场楼层权限与即时失效)。

## 实际修改

- 服务端按当前员工、资源、工具和楼层重新校验；显式越界参数整次拒绝。个人空权限、损坏权限不回退到部门放行。
- SSE 两个入口的拒绝探测统一到 Java 实际拦截的 `/mcp2/message`。工具身份参数由服务端签名覆盖，并从员工与模型工具参数中移除；模型工具说明声明当前楼层。
- 新增授权目录长轮询。管理操作提交时通知客户端，同时中断受影响的在途请求。结果返回前再次校验；撤权后再恢复相同权限也不能返回旧请求结果。
- Host 注销旧工具并取消旧调用；迟到的工具发现不能重新注册。连接器页面更新楼层说明，无法验证当前权限时清除旧展示。原有工具句柄在失效后不可继续调用。
- 员工详情切换时清空旧表单，旧员工保存响应不得覆盖新员工的权限草稿。详情连接检查也丢弃旧版本响应。

## 上线条件与剩余事项

1. 企业服务和客户端需一起发布，反向代理应允许至少一个服务端长轮询等待周期；企业连接超时应大于服务端 `mcpTimeoutMs`。
2. LFClaw 的 `LFCLAW_MCP_PERMISSION_SECRET` 必须与 Java 的 `lfclaw.permission.secret` 一致。Java 若配置 `lfclaw.permission.mcp-id`，值必须等于企业连接器 ID。当前执行环境未提供有效共享密钥，真实员工签名与真实业务数据的线上验收尚未执行。
3. 部署层须限制上游 MCP 直连，覆盖 SSE、消息 POST 和别名入口，只允许企业网关及明确批准的服务。否则员工可以绕开 LFClaw 使用无签名旧入口；在不改 MCP 源码的约束下，该限制是完整隔离的必要条件。
4. 即时通知适用于单进程 `JsonStore` 与管理接口写入，不支持多进程共写文件或外部直接改库。网络异常被检测后清除旧工具，服务端每次调用仍按现权校验。
5. 撤权不会擦除已经交付到历史会话中的数据；本次阻止的是后续调用与未返回的旧结果。MCP 查询逻辑变更后需重新审计工具范围。

下一步按版本化发布流程部署企业服务与桌面，配置匹配密钥和上游访问限制后，用真实一层/二层测试账号核验改权及越权拒绝。
